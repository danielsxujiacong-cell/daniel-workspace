# Project context

## V4.5.2 deployment boundary

Public delivery now uses same-origin EdgeOne KV with two checked-in static fallback slots. No live upstream dependency is necessary to browse. EdgeOne Functions call BigModel directly; private AI authenticates the existing owner via `/auth/v1/user`, public AI derives context exclusively from server-published data. No business tables or source project materials change. `WORKSPACE_PUBLIC` KV binding is mandatory for anonymous quota enforcement and publication writes; fail closed until the approved free namespace can be created after provider review. The existing EdgeOne service region excludes mainland nodes; mainland mobile testing remains external acceptance. No paid plan or alternative resources are authorized.

## Goal

Build a usable personal workspace that brings projects, notes, decisions, tasks, and work logs into one place. The default read-only Project Control Dashboard consumes only a fixed, automatically sanitized snapshot manually published by the authenticated owner to a dedicated Cloudflare KV namespace. After Supabase authenticates the allowlisted account, the same UI switches to the live private workspace; Supabase rows, RLS, synchronization, and local Git/filesystem state remain private.

## Scope

- In scope: Email/password login for the existing Supabase Auth owner, a public read-only default route backed by an owner-published KV JSON snapshot, and the same Dashboard/project/task/work-log/knowledge/decision components in public and private modes. The explicit `?mode=demo` route retains the isolated in-memory TK-1001 simulation. Private mode retains live Supabase, GitHub, Companion and AI behavior; public mode must dynamically skip store, cloud sync, Companion, Auth, AI and private GitHub modules. One owner-only button generates and publishes all available allowlisted data after automatic sensitive-value filtering; missing external activity is marked partial and does not block safe projects; failed writes preserve the previous snapshot. Home pinning syncs per user through `workspace_projects.is_pinned`; no project completion percentage is inferred. Cloud-backed project list/detail and CRUD, RLS-protected sync, a user-approved one-time local migration, GitHub snapshots, local read-only Companion, global search, contextual GLM AI, and device-local theme remain in scope.
- Out of scope: Public registration, Google login, password recovery flow, RAG, GitHub write operations/automation, scanning outside the fixed project root, automatic document-body ingestion, PDF or live-web parsing, real-time collaboration, fully autonomous agents, and permission management.

## Constraints

- Vanilla HTML, CSS, and JavaScript with no build step; `supabase-js` is loaded from a pinned-major CDN import for Auth only.
- The public `index.html` entry loads only `src/auth/gate.js` after displaying a static loading skeleton. The root route never reads a saved Supabase session or initializes Auth; it mounts `src/app.js` immediately in explicit public mode and fetches the fixed public snapshot in the background. Public mode may import shared presentation and snapshot-validation helpers, but must not import/read `src/store.js`, query Supabase, access Workspace/scan-cache storage, contact Local Companion, Codex Runner, AI or private GitHub endpoints. Only explicit `?mode=login` checks a saved session and must validate the allowlisted user with `getUser()` before loading the private live mode. Logout and unexpected `SIGNED_OUT` return to the public root without a redirect loop. `?mode=guest` aliases public mode; only `?mode=demo` loads the isolated in-memory simulation.
- `GET /api/public/snapshot` reads only the fixed `latest` value from `PUBLIC_WORKSPACE_SNAPSHOTS`, with `no-store`, and never queries private data. v1 remains readable for compatibility; POST requires v2. The private publisher freezes already loaded presentation fields/counts without refreshing GitHub, AI or work logs. POST verifies the exact configured owner via Supabase Auth, applies shared `src/static-snapshot.js` field projection, then replaces the complete JSON in one KV put. Missing external counts remain partial. No repository URLs, commits, raw notes, task/log bodies, knowledge/decision bodies, AI originals, credentials or paths are published. Only the existing reviewed release artifact supplies delivery text/links. KV propagation can temporarily expose the previous complete version, never a partly written object.
- V3.7-D project cards use only the explicit online URL field after HTTP(S), credentials, repository-host and local/private-host checks; never derive a website from a GitHub repository or guessed Pages URL. Project details show curated reader-facing facts and existing validated commits/work logs; keep SHA, repository status and device paths inside the collapsed technical section.
- External project and demo websites open only after the visitor clicks their reviewed URL. Real business demos and simulated workflows must be clearly distinguished; keep TK-1001 mutations in the current page's memory.
- `src/auth/config.js` may contain the Supabase project URL, public anon/publishable key, and one allowed user UUID or email. A blank allowed-user value denies everyone. Disable new-user signups in the Supabase project settings; never include a service role key, database/user password, or private token in browser code or GitHub.
- The existing `daniel-workspace-v1` key is a legacy local source. On login, offer a one-time migration only when real local records exist and the corresponding cloud tables are empty. Skip unchanged demo records, use insert-only conflict-ignore migration, and preserve the old key. If cloud data already exists, load it without overwriting it.
- V2.6 syncs only explicit Task, Knowledge, Decision, and Project base fields through the authenticated Supabase client. Each query is scoped to the validated `user.id`; RLS enforces `auth.uid() = user_id`. Project local paths and GitHub snapshots, Companion scan inventory/cache, filesystem metadata, Git clean/dirty, ahead/behind, branches, HEADs, commits, and local changes must never enter cloud row serializers.
- V3.1-B adds only `workspace_projects.is_pinned boolean not null default false`. Apply `supabase/v3.1-b-project-pinning.sql` before using pin controls; the client detects a missing field and keeps those controls disabled. A pin action updates only `is_pinned`, filtered by the validated user ID and project ID, so it cannot replace other project fields. Existing RLS remains in force.
- V3.7-C humanizes the five pinned-project introductions and recent progress at render time. A curated one-line intro is used only when the saved description is empty or contains scanner/README stage metadata; ordinary descriptions stay authoritative. The project editor can change one project at a time, and an unchanged displayed fallback must preserve the saved description when another field is edited. Home reads recent work logs through the existing authenticated, user-scoped read function; do not sync, bulk-update, or send evidence URLs. Progress copy uses verified commit summaries/work logs, retains the original GitHub commit URL, and never invokes AI during page rendering.
- V2.8 Task descriptions and AI suggestion source keys sync only through the authenticated serializer and additive `supabase/v2.8-task-suggestions.sql` migration; retain per-user RLS and never serialize local paths. The migration must be applied before claiming cloud sync for these new fields.
- Keep a separate authenticated cloud cache and sync baseline in browser localStorage for offline fallback. Theme, activity timeline, Local Companion inventory, scan baselines, project paths, and GitHub read-only snapshots remain device-local. The Supabase session is stored separately by the Supabase client. On logout, clear the private DOM and in-memory app/scan/cloud data and abort any active Companion request, while preserving localStorage for the next login on this browser.
- Fresh-install demo records must contain generic sample content only: no real project names, private paths, or personal repository links.
- Persist user content in browser `localStorage`; data does not synchronize between browsers or devices in V1.
- Store the theme preference in the same versioned workspace object under `settings.theme`; use `system` by default and preserve the selected theme during demo reset.
- Deleting a project keeps its tasks, knowledge, decisions, and activity, while clearing their project association.
- The companion binds only to `127.0.0.1`, serves allow-listed app files and a read-only `GET /api/local-projects`, and scans only `D:\_Codex project`. Skip hidden folders and common dependency/build/cache directories. Never write into scanned projects or issue network Git commands.
- `action_runner.py` is a separate `127.0.0.1:4175` service with exact page-origin and scanned-project allowlists. Accept only fixed `send_to_codex` missing-document types; do not accept command strings, arbitrary paths, or free-form model prompts. Codex uses a read-only sandbox to produce a draft; a second UI confirmation is required before creating the one missing README, HANDOFF, TODO, or PROJECT_STATUS file with create-only semantics.
- Dashboard model text is not an action authority. Bind its issue type to the locally detected issue and derive `projectId` and `allowedActions` in application code. A Task source key uses a stable name/type digest and never includes or hashes a local path.
- Project discovery uses Git roots and non-Git folders with common project documents/markers. Read Git branch, porcelain status, HEAD, local `origin/main`, ahead/behind, latest local commit and filesystem modification time. Set `GIT_OPTIONAL_LOCKS=0`; do not fetch, pull, commit, push, checkout, or mutate repositories from the scanner.
- Document discovery checks root and `docs/` filenames for README, HANDOFF, PROJECT_STATUS, TODO, PROJECT_CONTEXT, and CHANGELOG; do not read their contents. V2.4 stores a compact comparison baseline through `src/store.js`. Per the V2.4.1 offline-retention requirement, the last successful inventory is also stored in a separate browser-local cache (including its existing project names and paths) so the Dashboard can remain useful offline; label cached data as possibly stale. Neither cache is written into scanned projects or synchronized across devices.
- Match scanner records to workspace projects by sanitized GitHub owner/repository identity first, then exact local path/name. Only use valid HTTP(S) links in the UI.
- Treat local path and URLs as user-entered project metadata outside the fixed scanner root; never scan or operate those destinations.
- Read GitHub metadata only for valid public `https://github.com/{owner}/{repo}` URLs through unauthenticated public REST GET requests. Persist successful normalized snapshots inside the existing workspace object; on failure, retain the previous snapshot.
- If the anonymous Pages endpoint does not disclose its URL while the public repo reports Pages enabled, derive the conventional default GitHub Pages URL and mark it as estimated in the UI.
- Escape rendered user strings and allow only HTTP(S) project links.
- All Assistant chat requests go through `src/ai/service.js` to the dedicated `daniel-workspace-api` Cloudflare Worker; the Worker alone calls BigModel at the configured `AI_BASE_URL` with `AI_MODEL=glm-4-flash-250414`.
- `AI_API_KEY` belongs only in the Cloudflare Worker Secret set through Wrangler. Never expose it to browser code, GitHub, localStorage, or logs. Do not use Supabase service_role from the Worker.
- The `POST /api/chat` contract uses `{ message, currentPage, currentProject, relevantContext, history }`; success responds with `{ message: { role: "assistant", content }, provider: "real", model }`. Errors use `{ error: { code, message }, provider: "real", model }` and must remain visible/retryable; never silently switch a configured real provider to Mock.
- Build an explicit bounded context from the visible Workspace page. Include selected text when present, Tasks, Project summaries, Knowledge, Decisions, and a small Companion health summary. Exclude local absolute paths, repository and Pages URLs, credentials, session data, user identifiers, Git hashes, and full local file contents. Retain at most 20 recent chat messages and cap the request size.
- V3.3 project next-step suggestions use only bounded project description/status/stage/current next step, task title/status/priority/due date (supplemental and optional), and a verified public GitHub commit summary/time. Project description plus verified commit summary/time are sufficient to call GLM. Keep suggestion and manual edits in page memory; require an explicit adoption click before changing `project.next` through existing `persist()` and cloud serialization. Do not add fields, alter `src/cloud/sync.js`, use Mock fallback, claim unsupported progress, or expose this feature in guest mode.
- V3.4.1 Home daily briefs must analyze verified public commits from the last 24 hours first and commits from days 1–7 as a separately labelled supplement. Do not present older commits as recent. V3.6 also permits a recent saved work log as recommendation evidence, still requires an observable acceptance result, filters generic `next` values, and never substitutes task creation for a development action.
- V3.4.2 brief requests send project context once, use a bounded GLM output budget, and allow one safe upstream retry. Cover Worker response-body reads with timeouts and surface the returned reason. Keep normal Assistant request budgets unchanged.
- V3.6 work logs use a new additive `workspace_work_logs` table and never enter the existing four-table diff sync. Store only approved work-log fields, enforce `auth.uid() = user_id`, grant `authenticated` SELECT/INSERT/UPDATE only, and expose no delete operation. Validate evidence URLs as HTTP/HTTPS and cap them at 10 per record. AI receives evidence counts and bounded work text, never evidence URLs, project IDs, local paths, or Git hashes. Daily and weekly summaries require the real GLM Worker and discard output that cannot match a source record or verified commit.
- V3.8 Home activity reads only date, project ID, and row ID from the existing work-log table, scoped by the validated user and all current cloud project IDs. GitHub activity calls `/api/github/activity` with canonical repository names and bounded dates; the Worker requires the existing allowlisted Workspace session, uses GitHub App installation tokens for authorized repositories and Worker egress for public repositories, paginates commit history, deduplicates by repository + full SHA, and returns daily counts without hashes. Cache only those daily counts locally for one hour per account/range; never sync this cache or send it to AI.
- V3.8 activity ranges default to 30 days and support 7/30/90 days or custom dates up to 366 days. Failed or truncated repository reads and failed work-log reads remain visibly incomplete; unavailable history is never treated as zero. Status and stage charts use current Supabase snapshot values; blank or placeholder stage values are `未分类`, and no stage is inferred from commits.
